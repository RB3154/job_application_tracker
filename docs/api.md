# API Reference

Everything the `/api/...` endpoints do: resources and their rules, every endpoint, ownership, lookup lists, pagination, search and filters, PUT vs PATCH, and errors.

[← Back to the README](../README.md)

## Features

### Company Management

CRUD operations for companies:

- Create a company
- Retrieve companies one page at a time (see [Pagination](#pagination)),
  optionally searching by name (see [Search and Filters](#search-and-filters))
- Retrieve a company by ID
- Replace a company using PUT
- Partially update a company using PATCH
- Delete a company (only while it has no jobs; its locations go with it)
- Set the company's locations (see [Lookup Lists](#lookup-lists))

Only the user who created a company can change or delete it (see
[Ownership of Companies and Jobs](#ownership-of-companies-and-jobs)). The
website, if given, must be an `http://` or `https://` address.

---

### Job Management

CRUD operations for job postings:

- Create a job
- Retrieve jobs one page at a time (see [Pagination](#pagination)), with
  search and filters (see [Search and Filters](#search-and-filters))
- Retrieve a job by ID
- Replace a job using PUT
- Partially update a job using PATCH
- Delete a job (only while nobody has applied to it; its locations, skills,
  etc. go with it)
- Set the job's locations, work modes, skills, education requirements and
  sources in one request (see [Lookup Lists](#lookup-lists))

Jobs include information such as:

- Role
- Job description (optional)
- Job URL (must be an `http://` or `https://` address)
- Posting date
- Application deadline
- Minimum and maximum experience
- Salary information
- Company
- Locations, work modes, skills (required or nice to have), education
  requirements and where the job was found

Only the user who created a job can change or delete it (see
[Ownership of Companies and Jobs](#ownership-of-companies-and-jobs)).

---

### User Management

Operations for users:

- Register a user (with a password)
- Log in with email and password to receive a JWT access token
- Retrieve the logged-in user (`/me`)
- Partially update the logged-in user using PATCH `/me`
- Delete the logged-in user with DELETE `/me` (their applications and profile
  picture are deleted with them)
- Upload a profile picture with PATCH `/me/picture` (cropped to a 300x300 JPEG,
  max 5 MB, stored in AWS S3)
- Remove the profile picture with DELETE `/me/picture`
- Change the password with PATCH `/me/password` (needs the current password).
  Other devices are logged out; the response contains a new token for this one.
- Reset a forgotten password: POST `/forgot-password` emails a one-time reset
  token, and POST `/reset-password` uses it to set a new password (this logs
  out every device)

Users have:

- Username (unique ignoring upper/lower case, enforced by the database)
- Email (unique ignoring upper/lower case, validated, stored in lowercase)
- Password (at least 8 characters, stored only as an Argon2 hash)

A user can only change or delete their own account. Emails are only shown to
the user themselves.

Registration, login, forgot-password and reset-password are rate limited (see
[Rate Limiting](auth.md#rate-limiting)).

Everything is private: each user only ever sees their own companies, jobs,
lookup lists and applications.

---

### Application Management

CRUD operations for job applications (login required):

- Create an application for the logged-in user
- Retrieve the logged-in user's applications one page at a time (see
  [Pagination](#pagination)), optionally only one status (`?status=Interview`)
- Retrieve an application by ID
- Retrieve an application's status history
- Replace an application using PUT
- Partially update an application using PATCH
- Delete an application (its history goes with it)

Applications track:

- User
- Job
- Date applied
- Current application status
- Number of interview rounds so far (`interview_rounds`, starts at `0`)
- Private notes (optional, up to 5000 characters)
- Status history: every status change is recorded automatically (old status,
  new status, when), whichever page or endpoint made the change

Application IDs are generated by the database. A user can apply to a given job
only once, but different users can apply to the same job.

Users can only see and change their own applications. Requesting another
user's application returns `403 Forbidden`; an application that doesn't exist
returns `404 Not Found`.

Supported application statuses:

```text
Wishlist
Applied
Screening
Interview
Rejected
Offer
Accepted
Withdrawn
```

**Wishlist** is for jobs you want to apply to later. For a Wishlist item,
`date_applied` means the date it was saved. When it moves to any other status
(e.g. Applied), the server sets `date_applied` to today, unless the request
sends a date itself. My applications counts Wishlist items separately, so they
don't change the totals or the response rate.

## API Endpoints

The API currently exposes 56 operations: four primary resources plus five
lookup lists.

### Companies

```text
GET     /api/companies                          (?q= to search names)
POST    /api/companies
GET     /api/companies/{company_id}
PUT     /api/companies/{company_id}
PATCH   /api/companies/{company_id}
DELETE  /api/companies/{company_id}
GET     /api/companies/{company_id}/locations
PUT     /api/companies/{company_id}/locations   (replaces the whole list)
```

### Jobs

```text
GET     /api/jobs                    (search and filters, see below)
POST    /api/jobs
GET     /api/jobs/{job_id}
PUT     /api/jobs/{job_id}
PATCH   /api/jobs/{job_id}
DELETE  /api/jobs/{job_id}
GET     /api/jobs/{job_id}/details
PUT     /api/jobs/{job_id}/details   (replaces all locations, skills, etc.)
```

### Applications

```text
GET     /api/applications                           (?status= to filter; includes last_status_change)
POST    /api/applications
POST    /api/applications/quick                     (one step: finds or creates the company and job)
GET     /api/applications/{application_id}
GET     /api/applications/{application_id}/history  (oldest first)
PUT     /api/applications/{application_id}
PATCH   /api/applications/{application_id}
DELETE  /api/applications/{application_id}
```

All application endpoints require a valid access token. The owner is taken
from the token, so creating an application only needs a `job_id`; the
`application_id` is generated by the database.

### Users

```text
POST    /api/users          (register, public)
POST    /api/users/token    (log in, public; also sets the login cookie)
POST    /api/users/session  (Bearer token -> login cookie, for older sessions)
POST    /api/users/logout   (clears the login cookie)
POST    /api/users/forgot-password   (public, emails a reset token)
POST    /api/users/reset-password    (public, needs the emailed token)
GET     /api/users/me           (login required)
PATCH   /api/users/me           (login required)
DELETE  /api/users/me           (login required)
PATCH   /api/users/me/password  (login required, needs current password)
PATCH   /api/users/me/picture   (login required, multipart file upload)
DELETE  /api/users/me/picture   (login required)
```

### Lookup lists

The same four operations exist for each of `/api/locations`,
`/api/work-modes`, `/api/skills`, `/api/education` and `/api/sources`:

```text
GET     /api/skills              (your whole list, A-Z)
POST    /api/skills              (login required)
PATCH   /api/skills/{item_id}    (rename; login required, only while unused)
DELETE  /api/skills/{item_id}    (login required, only while unused)
```

Only sign-up, login, logout and password reset work without login. Every
other endpoint needs the access token and only works with your own data.

## Ownership of Companies and Jobs

Every company, job, lookup entry and application belongs to one user
(`user_id`). Nothing is shared and nothing is public.

- Lists, searches and pages only return your own rows.
- Someone else's company, job, list entry or application gets `404 Not
  Found`, exactly like one that doesn't exist, so you can't tell it exists.
- Company and job ids are always made by the server (they are unique across
  all users, so letting users pick them would reveal other users' ids).
- A job link is unique per user: two users can save the same link, each as
  their own job.
- Deleting your account deletes your companies, jobs, lists and applications.

---

## Lookup Lists

Locations, work modes, skills, education requirements and sources are private
per-user lists that jobs (and, for locations, companies) link to. Every list uses the
same JSON shape, whatever its table calls the columns:

```json
{ "id": 3, "name": "Pune" }
```

- You can add entries to your lists. Names are trimmed, and a name already
  in your list (ignoring upper/lower case) returns `409`.
- Renaming is always allowed (it only changes your own jobs). Deleting is
  only allowed while none of your jobs or companies use the entry (`409`).
- Ids are generated by the database.

A job's details are read and replaced together:

```json
PUT /api/jobs/backend-1/details
{
  "location_ids": [3],
  "work_mode_ids": [1],
  "source_ids": [2],
  "skills": [{ "skill_id": 7, "skill_type": "required" }, { "skill_id": 9, "skill_type": "preferred" }],
  "education": [{ "education_id": 1, "note": "or equivalent experience" }]
}
```

PUT replaces the whole set, so send the full lists every time (an empty list
removes everything of that kind). Unknown ids return `404` naming them
("Skill not found: 7"), and an id listed twice returns `422`. The response
contains the names, sorted A-Z. Company locations work the same way with
`{"location_ids": [...]}`.

## Pagination

The three list endpoints (`GET /api/companies`, `GET /api/jobs` and
`GET /api/applications`) return one page at a time instead of every row.

| Query parameter | Meaning | Default | Allowed |
| --- | --- | --- | --- |
| `skip` | How many rows to jump over | `0` | `0` or more |
| `limit` | How many rows to return | `10` (`items_per_page`) | `1` to `100` |

```text
GET /api/jobs?skip=0&limit=10     → jobs 1–10
GET /api/jobs?skip=10&limit=10    → jobs 11–20
```

These map straight to SQL `OFFSET` and `LIMIT`. Values outside the allowed
range return `422`.

Each response wraps the page in an object with the totals alongside:

```json
{
  "jobs": [ ... ],
  "total": 23,
  "skip": 10,
  "limit": 10,
  "has_more": true
}
```

The list key is `companies`, `jobs` or `applications`. `has_more` is `true`
while `skip + (rows on this page) < total`, so a client can keep requesting the
next page until it becomes `false`.

Results are always sorted so pages never overlap or skip rows:

| Endpoint | Order |
| --- | --- |
| Companies | `company_name` A–Z, then `company_id` |
| Jobs | `job_posting_date` newest first, then `job_id` |
| Applications | `date_applied` newest first, then `application_id` newest first |

All list endpoints and list pages share the `paginate()` helper in
`routers/helpers.py`, which counts the same rows the page query selects, so
`total` always matches the filters in use.

## Search and Filters

All filters are optional query parameters and can be combined with each other
and with `skip`/`limit`:

| Endpoint | Parameter | Meaning |
| --- | --- | --- |
| `GET /api/jobs` | `q` | Text found anywhere in the role or the company name (ignores upper/lower case) |
| | `company_id` | Only this company's jobs |
| | `location_id`, `skill_id`, `work_mode_id` | Only jobs that have this location / skill / work mode |
| | `open_only=true` | Hide jobs whose application deadline has passed |
| `GET /api/companies` | `q` | Text found anywhere in the company name |
| `GET /api/applications` | `status` | Only applications with this status |

```text
GET /api/jobs?q=backend&skill_id=7&open_only=true
GET /api/applications?status=Interview
```

An empty value (`location_id=`) means "no filter", which is what a search
form sends for "Any". A `%` or `_` in `q` is matched literally, not as a
wildcard.

The job filters live in the `JobFilters` schema and are applied by
`filter_jobs()`, which both `GET /api/jobs` and the `/jobs` page use, so the
page's "Load more" button filters exactly like the page did.

## Adding an Application in One Step

`POST /api/applications/quick` is what the **Add application** form uses. It
takes the fields a person knows when they've just applied and does the rest:

```json
{
  "company_name": "Google India",
  "role": "Backend Engineer",
  "job_url": "https://careers.google.com/jobs/123",
  "current_status": "Applied",
  "date_applied": "2026-10-30",
  "notes": "Referred by a friend"
}
```

Only `company_name`, `role` and `job_url` are required. The form's two optional,
folded sections can also send job details (`job_posting_date`, `application_deadline`,
`exp_*`, `salary_*`, `JD`) and company details (`company_site`, `company_description`).
New jobs and companies get them; existing ones only have their *empty* fields filled
in, so nothing saved earlier is overwritten. In one transaction:

1. **Job**: if a job with the same `job_url` already exists, it is reused
   (keeping its own company and role). The link is required because this is
   how duplicates are avoided.
2. **Company** (only when the job is new): an existing company with the same
   name, ignoring upper/lower case, or a new one created by the user.
3. New companies and jobs get ids made from their names (`slugify()` in
   `routers/helpers.py`): "Google India" -> `google-india`, and the job
   `google-india-backend-engineer`. If an id is taken, `-2`, `-3`, ... is
   added (`unique_id()`).
4. The application is created with its first history entry. Tracking a job
   you already track returns `409`.

The new job has no description and is posted "today"; you can fill in
the rest later on the job page.

## PUT vs PATCH

The API distinguishes between full replacement and partial updates.

### PUT

PUT performs a full replacement of the updateable fields.

Example:

```text
PUT /api/companies/COMP1
```

The complete update payload is expected.

### PATCH

PATCH performs a partial update.

Only fields included in the request are changed.

Example:

```text
PATCH /api/companies/COMP1
```

with:

```json
{
    "company_name": "Google India"
}
```

Only the company name is changed.

The implementation uses:

```python
model_dump(exclude_unset=True)
```

for PATCH requests so omitted fields are not overwritten.

## API Error Handling

The API handles common error conditions including:

- Resource not found
- Duplicate IDs
- Duplicate job URLs
- A user applying to the same job twice
- Duplicate usernames
- Duplicate emails
- Invalid foreign-key references
- Database constraint conflicts
- Invalid request data
- Missing, invalid, or expired access tokens (including tokens made before
  the last password change)
- Accessing another user's application (`403 Forbidden`)
- Changing a company or job you didn't create (`403 Forbidden`)
- Renaming or deleting a lookup entry that is in use (`409 Conflict`)
- Incorrect email or password at login
- Too many login or password reset attempts (`429 Too Many Requests`)
- Images that are broken, not images at all, or far too large in pixels
  (`400 Bad Request`)

HTTP status codes are used to communicate errors.

Examples:

```text
201 Created
204 No Content
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
```

Database `IntegrityError` exceptions are handled and converted into
appropriate API conflict responses.

For example, database constraint conflicts can result in:

```text
409 Conflict
```

instead of exposing raw database errors to the API client.

Application-level FastAPI exception handlers are defined in:

```text
main.py
```

The HTTP exception handler keeps response headers, so `401` responses include
`WWW-Authenticate: Bearer`.

The validation (`422`) handler passes the errors through `jsonable_encoder()`.
Errors from Pydantic model validators (e.g. "exp_max must be greater than or
equal to exp_min") contain Python exception objects that plain JSON can't hold;
without it, those requests would crash with `500`.

The handlers check the URL first. Requests to `/api/...` (and `/static`) get
the JSON error shown above. Pages opened in the browser, such as
`/jobs/does-not-exist`, get the HTML error page (`templates/error.html`)
instead of raw JSON.

Shared resource lookup and database conflict helpers are defined in:

```text
routers/helpers.py
```
