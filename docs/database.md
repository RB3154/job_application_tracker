## Database

The application uses PostgreSQL as its relational database.

The database connection is configured through:

```text
DATABASE_URL
```

The value is loaded from `.env` by the shared `settings` object in
`config.py` (see [Application Settings](architecture.md#application-settings)).

The SQLAlchemy database configuration is located in:

```text
database.py
```

The database layer provides:

- Async PostgreSQL engine
- SQLAlchemy `AsyncSession`
- Async session factory
- Declarative ORM base
- Async FastAPI database-session dependency

The PostgreSQL driver used by SQLAlchemy is:

```text
asyncpg
```

The SQLAlchemy connection URL is normalized to:

```text
postgresql+asyncpg
```

for asynchronous PostgreSQL operations.

## Database Schema

The database currently contains 17 tables:

```text
application
application_status_change
company
company_location
education_requirement
job
job_education
job_location
job_skill
job_source
job_work_mode
location
password_reset_tokens
skill
source
users
work_mode
```

The main entities are:

```text
Company                 User
   |                     |
   | 1-to-many           | 1-to-many
   v                     |
 Job                     |
   |                     |
   | 1-to-many           |
   v                     v
   +---> Application <---+
```

Each application belongs to exactly one user and one job. Jobs and companies
belong to one user (`user_id`), like applications (see
[Ownership of Companies and Jobs](api.md#ownership-of-companies-and-jobs)).

Each application has a status history in `application_status_change` (one
row per status change: `from_status`, `to_status`, `changed_at`).

Jobs also have many-to-many relationships with:

- Locations
- Work modes
- Skills
- Education requirements
- Sources

Companies have a many-to-many relationship with locations.

The many-to-many relationships are represented using explicit junction tables.
The lookup tables (`location`, `work_mode`, `skill`, `education_requirement`,
`source`) get their ids from the database (`GENERATED BY DEFAULT AS IDENTITY`).

## Database Constraints

The database schema contains relational constraints such as:

- Primary keys
- Foreign keys
- Unique constraints
- Composite primary keys
- Check constraints
- NOT NULL constraints
- Default values
- Indexes

Examples include:

### Job constraints

```text
application_deadline >= job_posting_date
exp_min >= 0
exp_max >= 0
exp_max >= exp_min
salary_min >= 0
salary_max >= 0
salary_max >= salary_min
```

`job_url` is unique per user (`uq_job_user_id_job_url`).

`user_id` references `users.id` with `ON DELETE CASCADE` (the same on
`company` and the lookup tables), so deleting an account deletes its data.
Link tables cascade too.

### Application constraints

`application_id` is generated by the database.

`user_id` references `users.id` with `ON DELETE CASCADE`, so deleting a user
deletes their applications.

The pair (`user_id`, `job_id`) is unique: each user can have at most one
application per job.

`interview_rounds` is required and defaults to `0` in the database
(`server_default`). The API rejects negative values with `422`.

`notes` is optional text (the API allows up to 5000 characters).

`application_status_change.application_id` references the application with
`ON DELETE CASCADE`, so deleting an application (or its user) deletes its
history.

Application status is restricted to:

```text
Wishlist
Applied
Screening
Interview
Rejected
Offer
Accepted
Withdrawn
```

### User constraints

`username` and `email` are unique ignoring upper/lower case: the unique
indexes are on `lower(username)` and `lower(email)`, so "Rudra" and "rudra"
can't both exist even if two sign-ups happen at the same moment. The API also
checks them first (for a clear `409` message) and stores emails in lowercase.

`token_version` (default `0`) is stored in every login token and goes up by
one when the password is changed or reset, which makes older tokens invalid
(see [Authentication](auth.md#authentication)).

`password_hash` is required. Plain-text passwords are never stored.

`image_file` is optional. It holds only the picture's filename; the picture
itself is saved on disk in `media/profile_pics/`.

### Password reset token constraints

`token_hash` is unique and stores only the SHA-256 hash of the emailed token.
`user_id` references `users.id` with `ON DELETE CASCADE`, so a user's reset
tokens are deleted with them. `expires_at` is required. Expired tokens are
cleaned up on every forgot-password request.

Foreign-key relationships are also validated before creating or updating
dependent records.

## Pydantic Schemas

Request and response schemas are defined in:

```text
schemas.py
```

Current schemas include:

### Company

```text
CompanyBase
CompanyCreate
CompanyResponse
CompanyUpdate
PaginatedCompaniesResponse
CompanyLocations
```

`company_site` must be an
`http://`/`https://` address (the `WebAddress` type).

### Job

```text
JobBase
JobCreate
JobResponse
JobUpdate
JobFilters
JobListQuery
PaginatedJobsResponse
JobDetails
JobDetailsResponse
```

`job_url` must be an
`http://`/`https://` address. `JobFilters` holds the search filters;
`JobListQuery` adds `skip`/`limit` to them for `GET /api/jobs` (FastAPI only
spreads a model into separate URL parameters when it is the route's only query
parameter).

### Lookup lists

```text
LookupResponse
LocationCreate, WorkModeCreate, SkillCreate, EducationCreate, SourceCreate
```

Every lookup list returns `{id, name}`. The five `...Create` schemas only
differ in the maximum name length (matching each table's column).

### Application

```text
ApplicationBase
ApplicationCreate
ApplicationResponse
ApplicationReplace
ApplicationUpdate
PaginatedApplicationsResponse
StatusChangeResponse
```

`ApplicationCreate` only takes the job and optional date/status/interview
rounds/notes; the owner is taken from the access token. A PUT that leaves out
`interview_rounds` resets it to `0`, since PUT replaces the whole application. `ApplicationResponse` includes both
`application_id` and `user_id`.

The `Paginated...Response` schemas wrap one page of a list together with
`total`, `skip`, `limit` and `has_more` (see [Pagination](api.md#pagination)).

### User

```text
UserBase
UserCreate
UserPublic
UserPrivate
UserUpdate
Token
PasswordChangedResponse
```

`UserCreate` includes the password. `UserPublic` (id, username, `image_file`,
`image_path`) is what anyone can see; `UserPrivate` adds the email and is only returned to the user
themselves. Neither includes the password or its hash. `image_path` is the
URL of the profile picture (e.g. `/media/profile_pics/<file>.jpg`), or `null`
if the user hasn't uploaded one. `Token` is the login response (`access_token`, `token_type`).
`PasswordChangedResponse` is the change-password response: a message plus a
fresh token, because the old one stops working.

The `*Update` (PATCH) schemas type required fields as `str = Field(default=None)`
on purpose: a field that is left out is skipped, while an explicit `null` is
rejected with `422`, so required columns can't be set to NULL (see the comment
on `CompanyUpdate`).

Pydantic is responsible for validating API input before it reaches the
database.

Examples of validation include:

- Required fields
- String lengths
- Non-negative experience values
- Non-negative salary values
- Valid date ranges
- Valid salary ranges
- Valid experience ranges
- Valid application statuses
- Valid email addresses (`EmailStr`)
- Minimum password length (8 characters)
- Web addresses starting with `http://` or `https://`
- No duplicate ids in a job's details

## Pydantic and SQLAlchemy Integration

Response schemas use:

```python
model_config = ConfigDict(from_attributes=True)
```

This allows Pydantic response models to be created from SQLAlchemy ORM
objects.

The general flow is:

```text
PostgreSQL
    |
    v
SQLAlchemy ORM object
    |
    v
Pydantic Response Schema
    |
    v
JSON response
```

Alembic is used for database schema migrations.

The migrations are:

```text

Revision: 9a7a9755e6a4
Revises:  a3f9c1d7e520
Message: add interview rounds to applications

Revision: aeca756ae956
Revises:  9a7a9755e6a4
Message: add created_by to company and job

Revision: fb8f1d0d8193
Revises:  aeca756ae956

Revision: a7cf23241ad4

Revision: e0b41fa1a607

Revision: 797444886326

```

Alembic is the only thing that creates or changes tables. The app itself never
does (see [FastAPI Lifespan](architecture.md#fastapi-lifespan)).

The `2bc8d0960952` migration:

- Creates the `users` table
- Adds a required `user_id` column to `application` with an
  `ON DELETE CASCADE` foreign key
- Replaces the unique `job_id` constraint with a unique (`user_id`, `job_id`)
  constraint
- Makes `application_id` database-generated using a sequence

> **Warning:** because existing applications have no owner, this migration
> **deletes all existing rows in `application`** before adding the `user_id`
> column. Back up any application data you want to keep before upgrading.

The `5c1e7a2f9d34` migration adds a required `password_hash` column to
`users`. It requires the `users` table to be empty, because existing users
have no password to fill it with.

The `8d4b2e6f1a73` migration adds an optional `image_file` column to `users`
for the profile picture's filename. Existing users simply get `NULL` (no
picture), so it is safe to run on a database that already has users.

The `a3f9c1d7e520` migration creates the `password_reset_tokens` table. It only
adds a new table, so it is safe to run on a database that already has users.

The `9a7a9755e6a4` migration adds a required `interview_rounds` column to
`application`. It was made with `alembic revision --autogenerate`. Because the
column is `NOT NULL`, it has `server_default="0"`: when the column is added,
PostgreSQL fills in `0` for every application that already exists. Without a
server default, adding a `NOT NULL` column to a table with rows would fail.

The `aeca756ae956` migration adds an optional `created_by` column (foreign key
to `users.id`, `ON DELETE SET NULL`) to `company` and `job`. Existing rows get
`NULL`, meaning "no creator, any logged-in user may change it".

The `fb8f1d0d8193` migration adds `token_version` to `users` with
`server_default="0"`, so existing users get `0`. After upgrading, tokens made
before it are no longer accepted and everyone has to log in again.

The `a7cf23241ad4` migration adds unique indexes on `lower(username)` and
`lower(email)` and drops the old case-sensitive unique constraints. It fails if
two users already differ only by case (e.g. "Rudra" and "rudra"); fix those
rows first.

The `e0b41fa1a607` migration makes the ids of the five lookup tables
database-generated (`GENERATED BY DEFAULT AS IDENTITY`) and starts numbering
after any ids already in each table.

The `8535d075e734` migration adds an optional `notes` column to `application`
and creates the `application_status_change` table. Applications that already
exist get one history row holding their current status.

The `5d81e862dbfe` migration makes `job.JD` (the description) nullable, so an
application can be tracked without pasting the description. Its downgrade
fills in empty descriptions before making the column `NOT NULL` again.

The `c797f6d44e3b` migration adds `'Wishlist'` to the allowed statuses. A
CHECK constraint can't be edited, so it is dropped and created again. Its
downgrade turns Wishlist items into `'Applied'` first, so the old rule fits.

The `797444886326` migration makes everything private: `created_by` becomes a
required `user_id` (rows without an owner go to the first user) on `company`
and `job`, the lookup tables get a `user_id`, links and names become unique
per user, and deleting a user cascades to all of it.

The Alembic environment has been configured to work with the project's
asynchronous SQLAlchemy engine while using Alembic's migration API.

### Apply migrations

```bash
uv run alembic upgrade head
```

### Check the current migration

```bash
uv run alembic current
```

### Create a new migration

After making approved SQLAlchemy model changes:

```bash
uv run alembic revision --autogenerate -m "description"
```

Autogenerate compares `models.py` with the real database and writes the
difference as a migration file in `alembic/versions/`. Generated migrations
should always be reviewed before applying them, then applied with
`uv run alembic upgrade head`.

To undo the most recent migration:

```bash
uv run alembic downgrade -1
```

### Check that models and database match

```bash
uv run alembic check
```

It prints `No new upgrade operations detected.` when `models.py` and the
database are in sync.

The `CheckConstraint`s in `models.py` are given explicit names (for example
`job_check1`) that match the names PostgreSQL gave them. Alembic compares
check constraints by name, so unnamed ones would make autogenerate think they
had been removed and add wrong `drop_constraint` lines to every new
migration.

## Database Creation

Create the empty PostgreSQL database once (for example in `psql` or pgAdmin):

```sql
CREATE DATABASE job_application_tracker;
```

Then `uv run alembic upgrade head` creates all the tables inside it.

The database schema itself is represented through the SQLAlchemy models and
managed through Alembic migrations.
